{{< alert level="warning" >}}
Модуль находится в стадии `Experimental`. API, конфигурация и custom resources могут меняться без предупреждения; не используйте его для продуктивных нагрузок.
{{< /alert >}}

Модуль `system-s3` предоставляет **системное** объектное хранилище S3 — то, в котором компоненты Deckhouse держат свои данные. Он поднимает один кластер Garage на control-plane узлах и выдаёт бакеты вместе с учётными данными через единственный custom resource.

Это не сервис хранения для приложений: пользовательские нагрузки получают объектное хранилище из модуля `sds-object`, где живут пользовательские бэкенды. Этот модуль существует, чтобы компонентам платформы было куда писать данные, не дожидаясь того модуля, и намеренно сделан меньше.

## Custom resource

| Ресурс | Scope | Назначение |
|--------|-------|------------|
| `SystemBucket` (`sb`) | Namespaced | Запрашивает бакет в системном хранилище и получает Secret с учётными данными S3 в том же namespace. |

Это весь API, и каждое отсутствующее поле — сознательное решение:

- **Нет ресурса для самого хранилища.** Модуль поднимает ровно один data plane, его настройки живут в `ModuleConfig`. Ссылаться не на что, и знать имя не нужно.
- **Нет отдельного ресурса доступа.** Учётные данные выдаются вместе с бакетом. Ротация — изменением аннотации `storage.deckhouse.io/rotate` на `SystemBucket`.
- **Нет политики хранения данных (reclaim policy).** Удаление `SystemBucket` удаляет бакет и все объекты в нём: компонент платформы владеет своим бакетом целиком.

## Кому доступен

`SystemBucket` принимается только в namespace с лейблом `heritage: deckhouse` — тем, который Deckhouse ставит на namespace каждого модуля. Проверка идёт по лейблу, а не по имени вида `d8-*`: имя — это соглашение, которое может воспроизвести любой пользователь.

Пользовательских прав на ресурс не выдаётся: видеть и менять его могут только администраторы кластера и хранилища (роли `d8:manage:permission:module:system-s3:*`).

## Data plane

Один кластер Garage, который разворачивает контроллер:

- по умолчанию три реплики с фактором репликации 3 независимо от числа control-plane узлов: реплики расходятся по одной на мастер, когда мастеров несколько, и уживаются на единственном мастере, когда он один;
- хранение — локальный том на узел для каждой реплики (`PersistentVolume` на `hostPath`, прибитый к узлу, в StorageClass `system-s3-local`), поэтому реплика возвращается на свой узел, а значит и к своим данным, после перезапуска;
- `storage.singleReplica` меняет всё это на одну реплику с фактором репликации 1.

{{< alert level="warning" >}}
Переключение `storage.singleReplica` на работающей инсталляции **уничтожает все данные в системном хранилище**: Garage не умеет менять фактор репликации на живом кластере, поэтому контроллер поднимает data plane заново и пустым. Бакеты создаются повторно, ключи доступа перевыпускаются автоматически — объекты нет.
{{< /alert >}}

Garage используется как есть, через его стандартный admin API. Он под лицензией AGPL — поэтому он обслуживает только хранилище самой платформы и никогда не предлагается пользователям как сервис.

## Удаление модуля

Выключение модуля удаляет его namespace, а вместе с ним нагрузку Garage, её
конфигурацию и Secret'ы. Две вещи при этом не удаляются, и обе существенны.

Пул локальных `PersistentVolume` — общекластерный, namespace его не забирает,
поэтому модуль удаляет его отдельно при выключении.

Каталоги, на которые эти томá ссылаются, — `/var/lib/deckhouse/system-s3/garage/`
на каждом control-plane узле — **остаются на месте**: у модуля нет агента на узлах
и дотянуться до них он не может. В них по-прежнему лежат объекты, которые были в
системном хранилище. Удалите их вручную, если данные не нужны, и учитывайте их
существование, если модуль будут включать снова.
